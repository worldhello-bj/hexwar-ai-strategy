# 运输（装卸）机制实测

本文件记录 **2026-10-15 在官方练习服上做的一次真实装卸采集** 的结果，目的是回答
「车内单位到底是什么、上车/下车后怎样变化」——这些无法从静态数据推断。

- 想定：`7527` 城市攻防作战（2V2）
- 服务器：练习服 `http://www.hexwar.cn/WARGAMEAI`（账号为普通选手，非管理员）
- 推演室：推演室7（服务端 `RoomID=228`，客户端目录 `/WARGAMEAI7/`）
- 两个账号：`USER_A`(UserID 1243，**导演**) + `USER_B`(UserID 1283，**红方**)
- 采集脚本：`tools/hex_transport_capture.py`、`tools/hex_2p_round.py`、`tools/hex_load_unload.py`
- 原始产物：`7527_transport_capture/`（**不入库**，属服务端数据）

> 边界：**行动点 / 时间消耗 / 分数**在装卸前后**观测不到差异**（见 §3），
> 这不等于"真的没有消耗"，只能说本方法测不出来。不要据此宣称整个仿真已与比赛规则一致。

---

## 1. 结论速览

| 问题 | 实测答案 |
|---|---|
| 车内的单位从哪来？ | 想定初始时它就在地图上，**与载具同格**（如蓝方 `步兵班@130032` 与 `装甲车@130032`）。它不是"隐藏记录"，而是正常已部署单位。 |
| 怎么装进去的？ | 用「上车」（`{"<单位>":{"inside":"<载具>"}}` → `com/ObjInto.asp`）。装车后该单位变成 `pos=0`、`blood=0`、`color=''`、`pos2=`载具格。 |
| 卸载后沿用原编号吗？ | **不沿用。** 服务端**新建一个实体编号**，并在新实体的 `id2` 里回指原记录编号。 |
| 原记录会怎样？ | **原样保留在车内状态**（`pos=0`/`blood=0`/`color=''`），既不删除也不恢复；它相当于"编制槽位"。 |
| 卸载有几种？ | 由 `off` 决定，`off` 的取值**就是乘员的 `typeid`**（1 人员 / 2 车辆 / 3 无人机·巡飞弹）。 |
| 分数/时间有变化吗？ | 三个阶段的 `Report_All.asp`（计分页）**逐字节相同**；`RoomSecond` 只按推演正常推进，**无法归因于装卸**。 |

## 2. 完整装卸循环（最完整的一组证据）

在**已开局**的推演里，对「初始同格的乘员 + 载具」做一次 上车 → 下车，
三个阶段各自抓完整快照（`load_unload_*/before.json|after_load.json|after_unload.json`）。

以 `load_unload_blue_armored` 为例（载具 `Obj_102069` 装甲车 M113TW，乘员 `Obj_102068` 步兵班）：

| 阶段 | 载具 `sons` / 动态 `son` | 乘员记录 | 新生成 |
|---|---|---|---|
| **初始** | `0` / `0` | `color=BLUE` `pos=130032` `home=130032` `blood=3` `pos2=130032` `car=Obj_0` | — |
| **上车后** | `1` / `1` | `color=''` `pos=0` `home=0` `blood=0` `pos2=130032` `car=Obj_0` | — |
| **下车后** | `0` / `0` | 仍为 `color=''` `pos=0` `blood=0`（**没被恢复**） | `Obj_102100`：`id2=Obj_102068`、`car=Obj_102069`、`pos=130032`、`blood=3`、`color=BLUE` |

另两组同样规律：

| 样本 | 载具 | 乘员 | `off` | 新生成编号（`id2` → 原记录） |
|---|---|---|---|---|
| `load_unload_red_support` | `Obj_102084` 火力支援车 ZBD100 | `Obj_102082` 步兵班 PLA2-191 | 1 | `Obj_102101`（`id2=Obj_102082`，兵力 4） |
| `load_unload_red_support_ugvs` | `Obj_102084` 同上 | `Obj_102083` 无人察打车 UGVS | 2 | `Obj_102102`（`id2=Obj_102083`，兵力 4） |

**要点**

- 上车是**就地隐藏**：原记录不删、`pos` 归零、`blood` 归零、`color` 清空；`pos2` 保留载具格。
- 下车是**新建实体**，不是"把原位单位放回来"。原记录**永远停在车内状态**，
  所以反复装卸会让实体编号不断新增。
- `car` 字段**不能**用来判断谁在车里：上车后乘员的 `car` 仍是 `Obj_0`，
  只有**下车产生的新实体**才带 `car=`载具编号。
- 载具的静态 `sons` 与动态 `son` 同步 ±1；**静态 `son` 图标串与动态 `sonarr` 恒定不变**。

### 未开局时同样成立

在「乘员已装车、但推演未开始」的旧会话上做的三次纯下车（`blue_armored_unload_01`、
`red_support_unload_01`、`red_support_unload_02_off2`）结果与上面完全一致
（`Obj_101953/101954/101955`，`id2` 分别回指 `Obj_100140/100154/100160`）。
说明这套行为**不依赖推演是否开始**。

## 3. 分数 / 时间 / 行动点

- `Report_All.asp`（夺控分 + 兵力分 + 战果分）在**初始 / 上车后 / 下车后**三阶段**完全相同**。
- `RoomSecond` 只是随推演自然推进（9→11→13 …），**不能归因于装卸**。
- 界面上没有出现"行动点"这类资源；装卸前后未观测到任何可归因的资源变化。
- 结论：**装卸在本方法下测不到代价**（既可能是真没有，也可能是代价只体现在客户端动画/计时上）。

## 4. `off` 的取值就是乘员的 `typeid`

| `off` | 放出的单位 | 乘员 `typeid` | 客户端菜单文字 |
|---|---|---|---|
| 1 | 人员（步兵班） | 1 | 下车 |
| 2 | 车辆（无人察打车 UGVS） | 2 | 无人车下车 |
| 3 | 无人机 / 巡飞弹 | 3 | 卸载 |

想定 7527 里，一辆红方火力支援车初始与 **步兵班 + 无人察打车 + 旋翼无人机 + 巡飞弹** 同格；
客户端的「全员下车」只连发 `off=1`、`off=2`，不含 `off=3`。

## 5. 接口契约（照抄官方前端）

**下车**（两段式，缺一不可）：

1. `GET /WARGAMEAI7/com/ComPost.asp`
   `ObjID=<载具>&Command={"<载具>":{"off":<n>}}&ObjColor=<阵营>&TaskName=下车|卸载&ObjPos=<格号>&MapID=`
   → **返回空串**（受理成功），服务端分配 `ComID`。
2. `GET /WARGAMEAI7/com/ComAjax.asp`
   → 取回 `ComID|UserID|{"ObjID":{"off":n}}|<时间>|下车`
3. `GET /WARGAMEAI7/com/Obj2_Out.asp`
   `ObjID=<载具>&ObjTypeID=<off>&Time1=<推演开始时刻>&ComID=<上一步>&ObjStack=0` → **返回 `True`**

**上车**（同样两段式）：

1. `ComPost.asp` … `Command={"<单位>":{"inside":"<载具>"}}&TaskName=上车`
2. `com/ObjInto.asp?ObjID=<单位>&CarID=<载具>&ComID=<ComID>` → **返回 `True`**

> `ComAjax.asp` 是**指令队列**，会把你之前提交的指令一起回放（队列不自动清空），
> 所以解析 `ComID` 时要按最新一条取，不要假设里面只有你刚发的那条。

## 6. 字段语义（修正此前的错误推断）

| 字段 | 语义 | 依据 |
|---|---|---|
| `sons`（静态）、`son`（动态） | **车内单位数量** | 上车 0→1、下车 1→0，两者同步 |
| 静态 `son` / 动态 `sonarr` | **固定图标串**，与车内有没有人、是谁**无关** | M113TW 在 `sons=0` 时 `son` 就已经是 `COD-M4,COD-FK,COD-98,YY2`（含车里没有的机型）；上车/下车后都不变 |
| `id2` | 平时为 `Obj_0`；**下车产生的新实体用它回指原记录编号** | `Obj_102100.id2 = "Obj_102068"` |
| `pos2` | 在车内时 = **载具所在格**；在地图上时 = 自身格 | 上车后 `pos=0` 而 `pos2=130032` |
| `car` | **只有下车产生的新实体**才指向载具；在车内时仍是 `Obj_0` | 上车后乘员 `car=Obj_0` |

> ⚠️ **勘误**：本文早期版本写过"载具静态 `son` 图标串里包含某单位的 `ico` → 那就是车内单位"。
> 这条**是错的**（图标串是固定的，纯属巧合），已删除。
>
> 可靠的判定法：**车内单位 = `pos=0` 且 `blood=0` 且 `color=''` 且 `pos2` 等于载具格的记录**；
> 再按 `typeid` 与想定编制对应（`off` 也只按 `typeid` 定位，服务端不靠编号关联）。

## 7. 如何真正开局（关键操作顺序）

**单账号开不了局**：导演身份 `RoomStart.asp` 返回 `-1`、红方身份返回 `0`，`StartTime` 始终为空。
**两个账号（导演 + 一个玩家）就能开局**。顺序不能错：

1. `quit` 退出原推演室（不退出则 `SetUpSave.asp` 报"您当前仍在某推演室未退出"）；
2. **初始化推演室**：`/WARGAMEAI<N>/Reset/Post.asp?scenarioId=7527&roomId=<N>`，
   GET 会返回一个**自动提交表单**（`param={"scenarioId":7527,"roomId":N,"backUrl":...}`），
   必须 **POST** 它才生效；大厅里状态码为 2 的房间点的就是这个；
3. 账号 A 以**导演**(`GameColor=NONE`) 进房：`POST SetUp/SetUpSave.asp` → 302 → `/WARGAMEAI<N>/Login/Login_Transfer/?PortID=N`；
4. 账号 B 以**红方**或**蓝方**进房（同上，`GameColor=RED|BLUE`）；
   ★ **推演一开始就不允许中途进入**（"推演已开始，不允许中途进入！"），所以两边必须**先都在座**；
5. 由**导演**调 `RoomStart.asp?AIStart=false&RoomSecond=0`；
   成功时返回 `Time1,WarDateTime,StartTime,b,c`（如 `2026/10/15 14:19:01,2026/10/15 14:19:01,2026/10/15 14:19:01,,0`）。

参考实现：`tools/hex_2p_round.py`（复位→双人进房→开局，并抓开局前后快照）。

## 8. 推演室 / 会话状态的其他事实

| 事实 | 证据 |
|---|---|
| 角色只有三种 | `SetUp/SetUp_Color.asp?RoomID=<RoomID>` 返回 红方 / **导演(NONE)** / 蓝方 三个按钮 |
| **每个推演室有独立的客户端目录** | `/WARGAMEAI<N>/`（推演室7→`WARGAMEAI7`，15→`WARGAMEAI15`）；`SetUpSave.asp` 的 302 Location 就是它。用错目录 → `User_Get.asp` 返回 `-1` |
| 登录态 cookie 的作用域 | `UserID/UserRoom/PortID/...` 写在 **`path=/WARGAMEAI<N>`**。所以直接请求 `/WARGAMEAI/SetUp/` 会回「请先登录」；要读大厅得临时把 `UserID` 也挂到 `path=/` |
| 大厅房间状态码 | `0` 可进入（大厅会让你选阵营）；`1` 正在推演、**不允许进入**；`2` 需先初始化 |
| `RoomStat.asp?RoomID=N` | 对自己**不在**的房间一律 `-1`（别人的对局也是 -1）→ **不能**用它判断别房是否在跑 |
| 初始化后的房间 | 36 条单位**全部已部署**、**车内为空**（所有 `sons=0`）；乘员与载具**同格** |
| 每次初始化都换新编号 | 旧会话是 `Obj_100136..100171`，本次重置后是 `Obj_102028..102063` → **编号是全局递增的**，不能写死 |

## 9. 编码坑（会让按中文匹配失败）

站点声明的 `Charset=GB2312` **不可信**：`/WARGAMEAI7/Obj_Get.asp` 实际是 **UTF-8**，
而 `Report_All.asp` 一页里甚至混着两种编码（中文用户名部分像 UTF-8、模板部分像 GBK）。
硬编码 `.decode("gb18030")` 会把 UTF-8 中文变成 `A杩炴鍏垫帓瑁呯敳杞�` 这种乱码，
**按 `army`/`name` 匹配单位就会全部落空**。稳妥做法是先试 `utf-8` 再退 `gb18030`
（仓库里即 `tools/hex_transport_capture.py` 的 `decode()`）。

## 10. 与离线引擎的差异（待办）

`engine/game.py` 按手册 3.3 实现上下车，用 `detail["carrier"]/["carried"]` 承载关系，
**单位编号不变**。真实服务端不是这样。若要对齐，至少需要：

- 上车：被装单位就地变 `pos=0`/`blood=0`/`color=''`/`pos2=`载具格，载具 `sons`+1；
- 下车：**新建**单位（新编号、`id2` 指向原记录），原记录保留在车内状态；载具 `sons`−1；
- 按 `off`(= 乘员 `typeid`) 逐个释放，一辆 4 乘员车要 4 次命令；
- 装卸**不影响**分数。

本次只做「数据补充」，**没有改动引擎**——是否改由使用者决定（策略环境可能依赖旧模型）。
