# 战斗 / 机动链路实测（进行中）

记录 2026-10-15 尝试「用脚本打一局并采集战斗数据」的过程与已确认结论。

> ★ **更新（2026-10-15 16:36）：机动"位置存错"已解决。**
> 根因：机动是 **三步** —— `ComPost`（下命令）→ `updatePos`（取本格耗时 ms）→
> **`MoveEnd`（提交这一步）**，而 `MoveEnd` 的 **`ObjNewPos` 必须是 mapid**（旧脚本传的是格号）。
> 受控实验 `tools/hex_move_probe.py`：传 mapid → 服务端 `pos` 正确；传格号 → `pos` 变成格号。
> 修正 `hex_combat_round.move_step` 后每一步 `服务端 pos == 期望`（全 ✔）。
> 下文第 3、6 节的"未解决"据此**作废**，仅作历史记录。

## 1. 已确认：7527 开局双方互相不通视

用引擎的通视判定（手册 4.4：高看低、观察点高程 +1 等级、连线插值）遍历开局全部
**144 对**蓝红单位：

> **通视的对数 = 0。**

也就是说，在 7527 的初始部署下，**任何蓝方单位都看不到任何红方单位**。
因此"开局直接开火"必然打不出战果——这不是接口问题，是地形与高程格局决定的。

同时高程（`map_hexes.json` 的 `elevation`，单位米）会通过**表3 高度差修正**
（`crt.atk_level_elev_fix`）影响攻击等级，高差 100 米以上还会直接禁止车辆通过。

## 2. 已确认：武器与目标类型必须匹配

一次实测：蓝方 `便携式防空导弹`（射程 20 格）在 **20 格**处打红方 `中型坦克`（复合装甲）
→ 接口受理成功（`com/ComPost.asp` 返回空串），但 20 秒内**无任何战果**。
原因：防空武器对地面装甲目标拿不到攻击等级，且距离贴着射程上限。

因此采集战斗数据必须：**先建立通视、再贴近到 3~6 格、并按目标类型选武器**。
（裁决表映射见 `engine/equip.py` / `engine/crt.py`。）

## 3. 未解决：脚本重放的机动改不了正确位置

机动链路（照官方客户端 `CommandMove` / `CommandUpdatePos`）：

1. `GET com/ComPost.asp` — `Command={"<ObjID>":{"move":"<格号1>,<格号2>","speed":0}}`
   `ObjPos=<格号1>&MapID=<格号2>&TaskName=机动&ObjColor=<阵营>` → 返回空串（成功）
2. `GET com/updatePos.asp` — `MapID`、`preIDhex`、`posIDhex`、`posIDcond`、`GridType`、`MapStep`…
   → 返回本格机动耗时（毫秒），如 `924` / `128` / `77`
3. `GET com/MoveEnd.asp` — 返回 `0`

**问题**：脚本按上述流程调用后，服务端把单位的新位置存成了**格号数值**而不是 mapid。
例如把单位从 `pos=170068`（格号 3434）走到格号 3435，服务端存成了 `pos=3435`，
而正确值应是 `pos=170070`。于是后续所有**距离与通视判定全部失准**，也就无法形成有效交战。

受控实验（同一单位、5 组参数组合，只调 `updatePos`）：**服务端位置一律不变**，
仅返回耗时。说明位置变更由 `ComPost` 的机动指令驱动，`updatePos` 只做确认/计时，
而脚本重放时这两者的配合与服务端预期不一致。**该参数语义尚未定死。**

## 4. HAR 证据：那批"车内单位"是真人点出来的

在真实浏览器抓包（`www.hexwar.cn.har`）里找到 **18 次 `com/ObjInto.asp`** 调用：

```
ObjID=Obj_100140&CarID=Obj_100141&ComID=0     ← 蓝方 A连步兵排 → A连步兵排装甲车
ObjID=Obj_100143&CarID=Obj_100144&ComID=0
ObjID=Obj_100146&CarID=Obj_100147&ComID=0
ObjID=Obj_100154&CarID=Obj_100156&ComID=0     ← 红方 1连 五个单位 → 1连火力支援车
…（红方 1/2/3 连各 5 个，共 15 个）
```

这正是此前 `snapshot/` 里那批 `pos=0 / blood=0 / pos2=载具格` 记录的来源：
**玩家在界面上点了"全员上车"**（对应客户端 `CommandGetOn` → `CommandOn` → `com/ObjInto.asp`）。
即：那份"已装车"的状态不是服务端准备阶段自动产生的，而是**一次真实的用户操作**留下的。

## 5. ★ 机动接口真值（已定死）

在**真实浏览器**里打开官方客户端 `/WARGAMEAI7/main.html` 并调用客户端自己的
`CommandMove(0, "<单位>", ["<frmMapid>","<toMapid>"], 0, 0, 0)`，抓到它实际发出的请求：

```
GET /WARGAMEAI7/com/updatePos.asp
 ?ObjID=Obj_102545
 &MapID=120037                     ← ★ 目标格的 mapid
 &ObjRot=180&GridType=2&MapStep=1  ← 目标格的 hextype / step
 &preIDhex=55&posIDhex=55          ← ★ 格的 `hex` 属性（地形贴图编号），不是格号！
 &posIDcond=0&HuiHe=1&steep=0
 &ComID=0&Index=1&Speed=0
 &RoomDay=0&RoomWeather=0&MineArea=0&GasArea=0&Bridge=0&EleLow=145&EleDiv=5
```

关键结论：

| 参数 | 真值 | 说明 |
|---|---|---|
| `MapID` | **mapid** | 地图格 `div` 的 **id 就是 mapid**（`80014`、`120037`…），不是那个 6 位的显示格号 |
| `preIDhex` / `posIDhex` | 格的 **`hex` 属性** | 地形贴图编号（本例 55）；**填格号会让服务端把单位存成错误位置** |
| `posIDcond` / `GridType` / `MapStep` | 格的 `cond` / `hextype` / `step` | 页面格 div 上就有这些属性，与 `snapshot/parsed/map_hexes.json` 完全一致 |
| `ComID` | `0` | 真实请求里就是 0 |

地图格 div 的实际结构（从浏览器读出，与本地解析表逐字段一致）：

```html
<div id="120037" elevation="200" cond="0" step="1"
     class="hexcolor50" hex="55" hextype="2"></div>
```

同一页面上还能直接读到 `高程` / `cond` / `step` / `hextype` / `hex`，
以及客户端全局变量 `Time1`（推演开始时刻）、`AIStart`、`RoomRound`。

## 6. 未解决：脚本重放仍改不对位置

即便按上面的真值传参，脚本重放后服务端存储的位置仍是**显示格号数值**
（走到格号 3435 就存成 `3435`，而正确应为 mapid `170070`），
说明 `ComPost` 机动指令与 `updatePos` 的配合还有一处没对齐。
**因此战斗数据仍未采到。**
