# 运输（装卸）机制实测

本文件记录 **2026-10-15 在官方练习服上做的一次真实「下车」操作采集** 的结果。
目的是回答一个此前无法从静态数据推断的问题：**车内单位到底是什么、卸载后会怎样变化。**

- 想定：`7527` 城市攻防作战（2V2）
- 服务器：练习服 `http://www.hexwar.cn/WARGAMEAI`（账号为普通选手，非管理员）
- 推演室：推演室7（服务端 `RoomID=228`，客户端目录 `/WARGAMEAI7/`）
- 操控身份：导演（`GameColor=NONE`，单人控红蓝双方）
- 采集脚本：`tools/hex_transport_capture.py`；原始产物在 `7527_transport_capture/`（不入库）

> ⚠️ 边界：本次 `RoomStart.asp` 取不到成功返回（导演身份 `-1`、红方身份 `0`），即推演
> **没有真正开始**（`StartTime`/`Time1` 为空）。单账号凑不出 2V2 的双方玩家，开局走不通。
> 因此这是一次「未开局状态下」的装卸采集：机制本身被验证，但**行动点/时间消耗、回合推进等
> 只在推演中才有的量无法从本次数据得出**。不要据此宣称整个仿真已与比赛规则一致。

## 1. 结论速览

| 问题 | 实测答案 |
|---|---|
| 车内究竟是什么单位？ | 数据库里**早已存在**这些单位记录，但处于「未部署」状态：`pos=0`、`blood=0`、`color` 为空、`car="Obj_0"`。 |
| 卸载后沿用原编号吗？ | **不沿用。** 服务端**新建一个实体编号**（本次为 `Obj_101953` / `Obj_101954` / `Obj_101955`），并在新实体的 `id2` 字段里回指原记录编号（如 `Obj_100140`）。 |
| 原记录会怎样？ | **原样保留**，不删除、也不会变成已部署。所以「只查新增编号」不够，但真实结果确实是**新增**而不是「旧记录转部署」。 |
| 乘员类型 / 生命值 / 位置 / 载具关系如何变化？ | 新实体 `typeid`/`ico`/`army`/`name` 与原记录一致；`color` 变成阵营色；`pos` = `home` = 载具所在格；`blood` = 编制兵力；`car` = 载具编号（真实绑定）。 |

### 三个样本

| 样本目录 | 载具 | 参数 | 车内单位数 | 新生成编号 | 新单位（`id2` → 原记录） |
|---|---|---|---|---|---|
| `blue_armored_unload_01` | `Obj_100141` 蓝方装甲车 M113TW | `off=1` | 1 → 0 | `Obj_101953` | 步兵班 `COD-M4`（`id2=Obj_100140`，兵力 3） |
| `red_support_unload_01` | `Obj_100156` 红方火力支援车 ZBD100 | `off=1` | 4 → 3 | `Obj_101954` | 步兵班 `PLA2-191`（`id2=Obj_100154`，兵力 4） |
| `red_support_unload_02_off2` | `Obj_100161` 红方火力支援车 ZBD100 | `off=2` | 4 → 3 | `Obj_101955` | 无人察打车 `UGVS`（`id2=Obj_100160`，兵力 4） |

三次都满足：载具静态 `sons` 与动态 `son` **各减 1**；无「消失编号」；新编号 `pos` = 载具格。

## 2. `off` 的取值就是乘员的 `typeid`

客户端把「下车」写成命令 `{"<载具ObjID>":{"off":<n>}}`。实测：

| `off` | 放出的单位 | 对应 `typeid` | 客户端菜单文字 |
|---|---|---|---|
| 1 | 人员（步兵班） | 1 | 下车 |
| 2 | 车辆（无人察打车 UGVS） | 2 | 无人车下车 |
| 3 | 无人机 / 巡飞弹 | 3 | 卸载 |

所以一辆红方火力支援车（`sons=4`）里通常是 **步兵班 + 无人察打车 + 旋翼无人机 + 巡飞弹** 各 1；
客户端的「全员下车」按钮只连发 `off=1` 和 `off=2`，不含 `off=3`（无人机/巡飞弹要单独"卸载"）。

## 3. 接口契约（照抄官方前端）

「下车」是**两段式**，缺一不可：

1. **提交**：`GET /WARGAMEAI7/com/ComPost.asp`
   `ObjID=<载具>&Command={"<载具>":{"off":1}}&ObjColor=<阵营>&TaskName=下车&ObjPos=<格号>&MapID=`
   → 服务端受理，**返回空串**，并分配一个 `ComID`。
2. **取回**：`GET /WARGAMEAI7/com/ComAjax.asp`
   → 返回 `ComID|UserID|{"ObjID":{"off":n}}|<时间>|下车`
3. **执行**：`GET /WARGAMEAI7/com/Obj2_Out.asp`
   `ObjID=<载具>&ObjTypeID=<off>&Time1=<推演开始时刻，未开局为空>&ComID=<上一步 ComID>&ObjStack=0`
   → **返回 `True`**，状态随即在下一帧 `Obj_Get.asp` / `ObjAjax.asp` 体现。

装载（上车）对称：`com/ObjInto.asp?ObjID=<单位>&CarID=<载具>&ComID=<ComID>`。

## 4. 字段语义（修正此前的猜测）

| 字段 | 语义 | 依据 |
|---|---|---|
| `sons`（静态） | **车内单位数量**，卸载后减 1 | `Obj_100141` 1→0、`Obj_100156` 4→3 |
| `son`（动态） | **当前车内单位数量** | 同上，与 `sons` 同步变化 |
| `son`（静态）/ `sonarr`（动态） | **图标字符串**，不是成员表 | 卸载后两者**都没变**（仍为 `COD-M4,COD-FK,COD-98,YY2`） |
| `id2` | 未部署时恒为 `Obj_0`；**卸载产生的新实体用它回指原记录编号** | `Obj_101953.id2 = "Obj_100140"` |
| `pos2` | 对"车内未部署"记录 = **载具所在格**；对已部署单位 = `0` | `Obj_100140.pos2=130032`（= 装甲车格） |
| `car` | 真实载具绑定；未部署时为 `Obj_0` | 新实体 `car="Obj_100141"` |

**"车内是哪个单位"的可靠判定法**：载具的**静态 `son` 图标串**里包含该单位的 `ico`。
例如 `Obj_100141.son` 含 `COD-M4`，而 `Obj_100140.ico = "COD-M4"` → 100140 就是它车内的那个步兵班。
（注意 `son` 串可能比 `sons` 长——红方 `ZBD100` 的 `son` 有 6 个图标但 `sons=4`，其中 `VUT5`/`RDOG`
在本想定里没有对应单位，说明这个串是"展示用图标位"，**不能当成员清单**。）

## 5. 与离线引擎的差异（待办）

`engine/game.py` 现在按手册 3.3 实现上下车：用 `detail["carrier"]` / `detail["carried"]` 承载关系，
**单位编号不变**。真实服务端不是这样：卸载会**新建实体编号**、原记录保留、用 `id2` 回指。

因此若要让离线环境与比赛一致，至少需要：

- 卸载时新建一个单位（新编号、`id2` 指向原记录），并保留原记录；
- 载具 `sons`/`son` 同步减 1，静态 `son` 图标串**不动**；
- 新单位的放置格 = 载具格，`car` 指向载具；
- 按 `off`(= 乘员 `typeid`) 逐个释放；4 乘员车要 4 次命令才能清空。

本次只做「数据补充」，**没有改动引擎**——改引擎属另一件事，需先确认策略环境是否依赖旧模型。

## 6. 推演室与会话状态（2026-10-15 第二轮补充实测）

为了采集「推演**进行中**」的装卸数据，又在练习服上把开局的每条路都试了一遍：

| 事实 | 证据 |
|---|---|
| 角色只有三种：**红方 / 导演(NONE) / 蓝方** | `SetUp/SetUp_Color.asp?RoomID=228` 返回三个按钮，导演的 `ColorOK('NONE','')` |
| **单账号无法开局** | `RoomStart.asp`：导演身份返回 `-1`，红方身份返回 `0`；两种身份下 `StartTime` 都保持为空 |
| 开局请求参数 | 客户端 `Start()`：`AIStart=<AIStart>&RoomSecond=<RoomSecond>`；成功时返回 `Time1,WarDateTime,StartTime,b,c` |
| 初始化推演室入口 | 大厅里状态码为 2 的房间会提示「是否初始化该推演室？」→ `../Reset/Post.asp?scenarioId=<想定>&roomId=<N>`。**它其实在客户端目录下**：`/WARGAMEAI<N>/Reset/Post.asp`，返回一个自动提交的表单，`param` 里是 `{"scenarioId":7527,"roomId":N,"backUrl":"../SetUp/SetUp_Transfer/"}` |
| 大厅房间状态码 | `0` 可进入（大厅会让你选阵营）；`1` 正在推演，**不允许进入**；`2` 需先初始化 |
| `RoomStat.asp?RoomID=N` | 对自己**不在**的房间一律返回 `-1`（连正在别人的对局里的房间也是 -1）→ **不能**用它判断别房是否在跑 |
| 初始化之后房间长什么样 | 36 条单位**全部已部署**（无 `blood=0` 记录）、**车内无乘员**（所有 `sons=0`） |
| 以红方身份进房 | 与导演身份一样：车内无乘员、`RoomStart` 仍不成功 |

> ⚠️ 由此得出一条重要修正：**「乘员已装车」本身是服务端准备阶段的产物，不是想定的静态编制。**
> 我们采到的那 15 条 `pos=0 / blood=0` 记录（含 `pos2` = 载具格），出现在那个**已经准备好、
> 但未开局**的旧会话里；而刚初始化的房间是「全部已部署、车内为空」。
> 初始化会清掉已装车的乘员，因此**那三个样本的状态目前无法简单复现**——快照已留存，但别误以为
> 随便进一间房就能看到同样的 `sons=1/4`。
